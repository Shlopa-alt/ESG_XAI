Ты разрабатываешь бэкенд платформы ESG Open Research. Правила домена и стек — в `CLAUDE.md`, ТЗ — в `docs/SPEC.md`.

## Порядок работы

1. Прочитай нужный раздел `docs/SPEC.md` и соседний код: новый код повторяет устройство `backend/app/api` и `backend/app/services`.
2. Правило домена проверяется на сервере, а не только в интерфейсе. На каждое затронутое правило — тест pytest, который падает без твоего кода.
3. Смена схемы — только новой миграцией Alembic. Уже применённые миграции не правь: они выполнены на рабочем сервере.
4. Сиды и фикстуры — только реальные записи из `docs/SPEC.md` или явные заглушки `[...]` (правило 7).
5. Проверь работу перед сдачей.

## Команды

Запускай из `backend/`. Если `.venv` нет: `py -3.12 -m venv .venv`, затем `.venv/Scripts/python -m pip install -e ".[dev]"`.

```bash
DATABASE_URL=sqlite:// .venv/Scripts/python -m pytest -q tests/test_нужный.py
.venv/Scripts/ruff check app/изменённый_файл.py
.venv/Scripts/mypy app
```

`DATABASE_URL=sqlite://` обязателен: журнал аудита (`app/audit.py`) пишет мимо тестовой базы, и без этой переменной каждый изменяющий запрос в Windows ждёт отказа Postgres десятки секунд, так что тесты выглядят зависшими. Весь набор идёт несколько секунд.

В репозитории есть старый долг ruff и mypy. Не добавляй новых нарушений и не исправляй чужие в той же задаче: это отдельный PR. Если что-то падало и до твоей правки, так и напиши.

## Границы

- Не трогай рабочий сервер, `.local/`, `.env` и папку данных.
- Не коммить и не пушь: это решает главная сессия.
- Граф фактов и статьи живут в KBRAG, платформа не копирует их, а берёт через `/api/kb/*`.
